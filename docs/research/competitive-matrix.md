# 同类项目与公开产品调研矩阵

调研日期：2026-10-22。以下内容只借鉴领域边界和交互共性，不复用第三方代码、界面或品牌。

| 项目/产品 | 类型 | 可借鉴 | 风险或不采用 |
|---|---|---|---|
| OpenEMR | 开源 EHR | 患者档案、预约、处方、FHIR、审计和多角色 | GPL-3.0；系统体量大，不适合作为首版底座 |
| OpenMRS | 开源 EMR 平台 | 模块化、元数据和可配置表单 | 面向资源受限环境的平台复杂度较高 |
| Medplum | FHIR 开发者平台 | OAuth/OIDC、FHIR API、React 组件和开发体验 | 完整 CDR 超出 MVP 范围 |
| HAPI FHIR | Java FHIR 服务 | 资源验证、互操作、服务端契约 | 引入 Java 服务会提高部署成本 |
| Android FHIR SDK | Android 医疗 SDK | 离线优先、本地缓存、FHIR 移动端 | 首版只参考离线模式，不接入完整 FHIR Store |
| OpenCare 类家庭照护项目 | 家庭协同 | 家属账号、任务、药物提醒、照护日志 | AGPL-3.0 且成熟度需进一步评估 |
| 国家医保服务平台等公共入口 | 公共医疗政务 | 实名账号、办事流程、消息和可追溯状态 | 不分析非公开接口，不复制受保护内容 |
| 医院微信公众号/小程序 | 患者服务 | 预约、报告、消息、家属绑定、无障碍 | 只观察公开流程，不采集登录后私有数据 |

## 共性结论

- 医疗系统的基础不是页面数量，而是持续一致的身份、组织、授权和审计。
- 长周期任务需要明确截止时间、完成证据和异常升级。
- 家属协同必须建立在患者授权而不是默认血缘关系上。
- 医生工作台需要异常优先排序，而不是让医生逐页寻找问题。
- 政府和药企属于不同数据域，不应复用医院内部管理界面。
- 离线能力必须处理幂等补传，否则重复点击会造成状态错误。

## 本项目的差异化

- 以“通用治疗路径模板”而非固定单病种为骨架。
- 将患者、家属、医生、医院、政府和药企放在一套可审计权限模型中。
- 政府使用最小人数抑制，药企使用机构和患者月双阈值。
- 官方公开数据以可追踪快照进入，不依赖未公开接口。
- 三个客户端共享 Python API，而 Android 与微信分别采用原生实现。
